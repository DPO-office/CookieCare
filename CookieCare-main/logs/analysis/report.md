# Redesign the report-generation/rendering phase

## Context

This session already fixed several PLAN/ACT/VERIFY bugs live (dropped compound requirements, blocked negotiation operation, a lossy evidence pool cap, a keyword-only retrieval fallback). Those fixes made the *substance* of compliance-check answers (Article 28, GDPR rights, transfers) materially more correct. But the user then compared our *output* against a competitor's report on the identical Article 28 question and found ours reads as unprofessional: one giant undifferentiated 5-column table, every status word bolded, every recommendation bullet's leading verb bolded with no clear reason, no severity grouping, inline `[E1]`-style citations that resolve to nothing, three rigid boilerplate sections ("Requirements at a glance" / "What needs attention" / "Missing materials") that appear identically regardless of what was actually found. The user's explicit instruction: don't patch this, do a real design pass — the report-generation phase is critical, "our plan and act system is not working fine... but the way we generate the report is very casual."

Three parallel Explore agents plus one Plan-validation agent (which read the render/synthesis pipeline, the outline-design code, the finding/severity data model, and the citation model in full) traced every symptom to a precise root cause, all confirmed at file:line and spot-checked directly. The core finding: **the rigid table-and-four-sections shape is not an LLM being lazy — it's a 100% hardcoded template (`buildBlufReport`) that runs for every `compliance_check` report today, and it deliberately prevents the LLM from writing its own structure.** A second, genuinely adaptive rendering path already exists in the codebase (and even has a tested-but-never-wired-up outline-refinement step) — the fix is largely to route to what's already built and remove hardcoded formatting rules, not to invent a new architecture from scratch.

Goal: make report *structure* adapt to what was actually found and what was asked (numbered sections, narrative synthesis + small local tables only where useful — like the reference doc), fix the meaningless bolding, surface the severity data that already exists as real Critical/Important/Minor grouping, replace two broken citation-marker systems with one real footnote system, and add a bounded mechanism for the system to flag genuinely relevant observations outside the explicit checklist.

## Ground truth (verified, file:line)

**The two report paths** — `backend/src/modules/analysis/capabilities/reporting/render-output.ts:272-280`:
```js
const usesDynamicOutlineLane =
  state.plan?.reportSpec?.reportType === "qa_answer" || !capabilityContract.allowBluf;
if (blufReportEnabled() && !usesDynamicOutlineLane) {
  rendered = await buildBlufReport(state, visible, spec);        // Path A — hardcoded
} else {
  rendered = await synthesizeReport(state, visible, spec, { retrySectionIds });  // Path B — adaptive
}
```
Only `compliance_check` has `allowBluf: true` (`capabilities/contracts/analysis-capability-contract.ts`), so every compliance_check report — the exact category this session's other fixes targeted — goes through Path A unless `reportType === "qa_answer"`. `ANALYSIS_BLUF_REPORT=1` is set in `.env`, so Path A is genuinely live (confirmed against `docs/CODEX-LIVE-E2E-COMPOUND-ASK-HANDOFF.md:256`).

**Path A (`buildBlufReport`, `render-output.ts:2193-2285`)** is fully hardcoded: literal `"## Bottom line"` / `"## Requirements at a glance"` / `"## What needs attention"` / `"## Missing materials"` string literals, table built entirely in code by `assessmentTableMarkdown` (`:1739-1765`). The only LLM call (`streamBlufBottomLine`, `:2098-2175`) writes one short paragraph and is explicitly told `"do not write a heading"`.

**Path B (`synthesizeReport`) already gets adaptive structure from `deriveReportOutline`** (`capabilities/plan/derive-report-outline.ts:118-308`, built at PLAN time via `buildFinalReportSpec` in `resolve-report-spec.ts:85-107`) — for `compliance_check`, each authored `PackageOutlineExtra` already becomes its own numbered `##` section (`:37-78,209-227`), with `groupAssessmentsForReport`'s token-similarity clustering (`shared/group-assessments.ts:58-96`) as fallback for the rest. **This machinery runs for every compliance_check request today and is simply discarded**, because Path A never reads `reportSpec.outline` — it always synthesizes its own fixed 4 sections directly from `assessments`.

**A ready-built outline-refinement step exists and is dead code.** `capabilities/plan/refine-report-outline.ts` (`refineReportOutlineViaLLM`, invariant-checked via `validateRefinedAnalysisItems`, has its own test fixture) refines/merges/splits analysis headings — exactly the "make section headings adapt" mechanism needed. `resolve-report-spec.ts:91` declares `enableRefine?: boolean` but nothing ever reads it — confirmed by grep: `refineReportOutlineViaLLM` is referenced only in its own definition file, nowhere in `build-plan.ts` or `build-branch-orchestration.ts`.

**Bold-everything root cause** — `backend/src/modules/analysis/prompts/memo-markdown-craft.ts`, `LEGAL_MEMO_MARKDOWN_CRAFT:14-19` and `TABULAR_SECTION_MARKDOWN_CRAFT:52-53`: the LLM is literally instructed, with example tokens, to bold `"Recommendation verbs at the start of each recommendation bullet (e.g. **Amend**, **Confirm**, **Obtain**)"` — every bullet, no exceptions. Imported into `prompts/synthesis.ts:98,523,572`, `prompts/report-sections.ts:287`, `prompts/render-output-prompts.ts:14-18`. Separately, `assessmentTableMarkdown` (`render-output.ts:1762`) unconditionally wraps every status cell in `**...**` — confirmed pure redundant noise: `frontend/src/shared/utils/markdownToHtml.ts`'s `STATUS_PATTERNS`/`injectStatusBadges` (`:59-147`) already colors status cells (green/yellow/orange/red) by stripping all HTML tags (including `<strong>`) before matching plain text — the badge system works identically with or without the bold wrap. That same badge list has no grey/neutral variant and doesn't match "insufficient data" / "not applicable" (renders unstyled today), and miscategorizes `"cannot determine"` as **red** (`:81`) even though it's an evidence gap, not a violation — exactly the status/rationale mismatch class of bug flagged earlier this session.

**Severity exists but the wrong field was assumed for grouping.** `Finding.severity?: "low"|"medium"|"high"` (`models/finding.ts:75`) is real for risk-lane/rule-lane findings but is **never set** by the mainline compliance_check aggregation path (`evaluate-package.ts` → `grouped-results-to-findings.ts` → `requirement-status-policy.ts`). What that path sets instead is `RequirementAssessment.judgement.materiality`, and `materialityFromFindings` (`capabilities/act/requirement-status-policy.ts:205-223`) — confirmed by direct read — unconditionally collapses **every** Gap-status assessment to `"high"` at line 217 (`if (compliance === "gap") return "high";`), before any per-finding value is consulted. So neither field gives real 3-way granularity across the assessments that populate the requirements table. Correct approach: bucket **assessments** by existing status-tier helpers (`isGapLike`→Critical, `isConditionalLike`→Important, `cannot_determine`/other→Minor — same helpers `severityRank`, `render-output.ts:2090-2096`, already uses for sort order), and bucket **risk findings** separately by their own reliable `Finding.severity`. Don't conflate the two populations.

**Citations are two incompatible, both-broken systems.** (1) `createCitationRegistry` (`render-output.ts:1210-1251`) is deterministic but keyed by **docId only** — two different clauses from the same document both render `[1]`; it builds a real reference list but maps number→document *title* only, never to a specific clause. (2) `[E1]`/`[E2]` markers used in narrative synthesis are **invented by the LLM**: `prompts/synthesis.ts:313` hands the model bare, unlabeled quotes (`e.quotedText.slice(0, 200)`) while the system prompt (`:694,724`) tells it to cite `[E#]` anyway — the model picks both which evidence to cite and what number to call it; the only downstream check (`merge-branch-outputs.ts:28-31`) just validates the number is in-range. No footnote list is ever built for these. Full clause text is **not** lost by render time (`locate-evidence.ts:15-17` retains 12k/24k chars on `Finding.evidence[].quotedText`; today's ~180-280 char truncations are all render-time `.slice()`/`cleanQuote()` calls) — a real footnote system with full text is feasible without re-fetching anything. The one missing field is `contextHeading` (the section heading a clause came from), present on the richer `SharedEvidenceItem` (`models/evidence-package.ts:51-71`) but dropped when downgraded to the minimal `EvidenceSpan` that reaches `Finding.evidence` — confirmed at `grouped-results-to-findings.ts:381-402`, reconstructed identically (without the heading) at 8 more call sites across `check-against-rule.ts`, `check-expected-clauses.ts`, `evaluate-matrix-row.ts`, `evaluate-package.ts`, `extract-clauses.ts`, `extract-playbook-positions.ts`, `flag-risk.ts`, `inventory-provisions.ts`.

**Frontend citation UI is dead code, confirmed and to be deleted per user decision.** `ReportView.tsx`'s `buildRefList`/`ReferencesPanel` (`:49-107`) reads `Message.sources`, which is never populated anywhere in `useAnalysis.ts`, and the backend never returns a `sources` field (`api/analysisJobs.ts:24-33`, `backend/.../api/controller.ts:82-91`). It's also shaped for a different concept entirely (web-source URLs with a Google-search fallback, no room for a clause quote or heading) — not reusable for real footnotes. **Decision: delete it** rather than repurpose or leave in place.

## Implementation plan — five phases, sequential, live-verified after each

Work exactly as the rest of this session has: read the exact code, make the smallest targeted change, typecheck, restart the dev server, verify live in the browser, check for regressions on a previously-passing question, before moving to the next phase. Do not batch phases together.

**Regression checklist to re-run after every phase** (all confirmed passing this session, all now at risk from routing/prompt changes — re-run verbatim, not just at the end):
- Q4 — "Perform a rigorous GDPR Article 28 compliance review... Present findings as a table." (explicit table request — must **stay** on a table-shaped path regardless of size)
- Q9a / broad "Analyze GDPR compliance" (no explicit shape — the main target for Phase 1's adaptive structure)
- Q12 — GDPR Articles 15-22 rights review
- Q13 — international transfer compliance
- Q8 — compound (Article 28 + playbook + top-5 risks) — exercises `designRiskOutline` alongside compliance_check in one report; a Phase 1 regression could show up as a structural clash between lanes here

### Phase 0 — Bold and status-color cleanup (ship first, independent, no routing risk)

- `capabilities/reporting/render-output.ts:1762` — remove the `**...**` wrap around `renderedAssessmentStatus(...)` in `assessmentTableMarkdown`. The frontend badge system doesn't need it; today it bolds every row equally (a "Strong" row identically to a "Cannot determine" row), which is exactly why nothing stands out.
- `prompts/memo-markdown-craft.ts` — in `LEGAL_MEMO_MARKDOWN_CRAFT`: delete the "bold every recommendation verb" rule (line 18) entirely. Soften the "bold status words" rule (line 15) to bold the overall verdict phrase once per section's lead sentence, not every status mention. Mirror both edits in `TABULAR_SECTION_MARKDOWN_CRAFT` (lines 52-53). Grep repo-wide for `"Recommendation verbs"` and `"Status words"` afterward to confirm no other prompt file duplicates the same instruction independently.
- `frontend/src/shared/utils/markdownToHtml.ts:59-84` (`STATUS_PATTERNS`) — add a neutral/grey variant; move `"cannot determine"` out of the `red` pattern into grey (it's an evidence gap, not a violation); add `"insufficient data"` / `"not applicable"` to grey. Add the matching `.md-status-grey` background/color rule if the CSS doesn't already have one (check `frontend/src/features/analyze/styles/analyzeStyles.ts` near the existing `.md-status-*` rules — `.md-status-grey` already exists per this session's earlier CSS read; confirm it's wired to the right hex before assuming).

### Phase 1 — Route large/unscoped compliance_check reports to the adaptive path

**1a — fix the routing gate.** `render-output.ts:272-280`: add a compliance_check branch to `usesDynamicOutlineLane`, e.g. `capabilityContract.operation === "compliance_check" && assessments.length >= N && spec.depth !== "narrow" && schemaId !== "brief_summary"`. The `schemaId !== "brief_summary"` guard is required to keep Q4's explicit "present as a table" request on the table-shaped path regardless of size — this is the specific regression risk identified against this session's own verified questions. Start `N` around 6-8 (roughly Q4/Q9a's assessment count vs. a single-article narrow lookup) and tune from live results. Log the branch decision through the existing `pacLog("RENDER capability contract", ...)` block (`:195-205`) so it's visible while testing.

**1b — wire up the existing (currently dead) outline refinement.** Actually call `refineReportOutlineViaLLM` (`capabilities/plan/refine-report-outline.ts:109-214`) from `buildFinalReportSpec` (`resolve-report-spec.ts:85-107`), consuming the already-declared `enableRefine` arg. Thread the flag from `build-plan.ts:442,600` and `build-branch-orchestration.ts:195`, gated on `reportType === "regime_compliance_memo"` and outline analysis-item count (the only complexity proxy available at PLAN time, since ACT hasn't run yet). This step already self-validates (`validateRefinedAnalysisItems` enforces the refined items partition the exact same `requirementIds` as the seed) and falls back to the seed outline on any failure — low incremental risk.

**1c — optional new outline designer, only if 1a+1b prove insufficient in live testing.** A `designComplianceOutline` mirroring `capabilities/plan/design-risk-outline.ts`/`design-comparison-outline.ts`, added at render time in `synthesize-report.ts:88-100`, seeded from `groupAssessmentsForReport`. Do not build this speculatively — verify what 1a+1b already produce first; the existing outline + refined headings may already read like the reference doc's numbered sections.

**Verify:** run the full regression checklist after 1a alone, then again after 1a+1b, before considering 1c.

### Phase 2 — Real "Summary of Findings" (Critical / Important / Minor), independent of Phase 1

Add a deterministic block (no LLM call) the same way `## Missing materials` is already appended in `buildBlufReport` (`render-output.ts:2271-2282`), as a shared helper near `assessmentTableMarkdown` (`:1739-1765`) so both `buildBlufReport` and the tail of `synthesizeReport`'s section assembly (`synthesize-report.ts:208-217`) can call it — lower coupling than threading it through the PLAN-time outline system.

- Bucket **assessments** by status tier using the existing helpers: `isGapLike` → Critical, `isConditionalLike` → Important, `cannot_determine`/other issue statuses → Minor. Do not use `judgement.materiality` for this (confirmed collapsed to "high" for all Gap statuses — see Ground truth above).
- Bucket **risk findings** (today's flat "Key risks" list) separately by their own `Finding.severity`, which is reliable in that lane.
- Replace today's flat `## What needs attention` list and flat severity-sorted `## Key risks` list with this grouped section.
- Check placement against `enforceConclusionSectionLast`'s reordering logic (`prompts/report-sections.ts:431-460`) — a naively-appended block will land after Conclusion unless explicitly excluded from or inserted before that reordering pass, and the reference doc places this section before the closing narrative.

### Phase 3 — Real footnote-style citations

Sequence alongside or after Phase 1 (touches the same evidence-construction call sites a future 1c designer would also read from).

1. Add `contextHeading?: string` to `EvidenceSpan` (`models/locator.ts:14-20`) — additive.
2. Thread it through at the ~9 conversion sites, sourcing from `SharedEvidenceItem.contextHeading` (`models/evidence-package.ts:58`) wherever the call site has that bundle item available: `grouped-results-to-findings.ts:381-402` (start here — the dominant path), then `check-against-rule.ts`, `check-expected-clauses.ts`, `evaluate-matrix-row.ts`, `evaluate-package.ts`, `extract-clauses.ts`, `extract-playbook-positions.ts`, `flag-risk.ts`, `inventory-provisions.ts`. Where a site doesn't go through `SharedEvidenceItem` at all, leave it `undefined` — acceptable degradation, not a blocker.
3. Replace both marker systems with one deterministic per-clause registry: extend `createCitationRegistry` (`render-output.ts:1210-1251`) so the key is `docId+structuralPath+charRange` instead of `docId` alone, assigning a stable number the first time a specific span is cited, with a lookup callable before generation.
4. Fix the actual "invented markers" root cause: `renderThemeGroupMembersOnly` (`prompts/synthesis.ts:304-336`, quote-building at `:313`) currently hands the LLM bare unlabeled quotes. Change it to print `[${registryNumber}] "quote"` using the new registry, so the model echoes an existing number instead of inventing one — requires threading the registry instance into `buildSectionSynthesisUserPrompt` (`synthesize-report.ts:132-138`), which doesn't receive one today.
5. Build a real deterministic `## Citations` section (extend `appendReferences`, `render-output.ts:1253-1257`) with full untruncated `quotedText` + `contextHeading` + source document title, footnote-style, keyed by the same registry numbers.
6. Update `merge-branch-outputs.ts:28-31`'s marker-range validation to match the new scheme.
7. Delete the dead frontend citation UI: `buildRefList`/`ReferencesPanel` in `ReportView.tsx` (`:49-107`) and the unused `sources` field on `Message`/`AnalysisJobResult` (`frontend/src/features/analyze/types.ts`, `api/analysisJobs.ts:24-33`) — per the confirmed decision to delete rather than repurpose, since the new footnotes live inline in the markdown.
